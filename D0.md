# Changelog

Running log of what changed and why. Newest at the bottom.

## Network-wide uBlock parity

Goal: make ublproxy block what uBlock Origin blocks, on YouTube especially, without a
browser extension. Started from three rules pasted into the portal:

```
youtube.com##ytd-ad-slot-renderer
youtube.com##ytd-rich-item-renderer:has(> ytd-ad-slot-renderer)
www.youtube.com##+js(json-prune, playerResponse.adPlacements playerResponse.playerAds playerResponse.adSlots adPlacements playerAds adSlots)
```

The first two already worked. The third did nothing. Chased that down and it turned into
the list below.

### json-prune only hooked JSON.parse

`internal/blocklist/scriptlets.go` patched `JSON.parse` and nothing else. YouTube pulls its
player and feed data from the Innertube API over `fetch`, and reads it with
`Response.prototype.json()`. Nothing ever called the patched `JSON.parse`, so the scriptlet
was dead code on the exact site it was written for.

Added a `Response.prototype.json` hook and brought the path syntax up to what uBlock
actually accepts: needle paths as a precondition, and the `[]`, `*`, `{}`, `[-]`, `{-}` tokens for
arrays and for objects whose keys you can't predict.

### The needle argument is optional, and that is the point

`json-prune` takes `json-prune, prunePaths, needlePaths`. The *second* argument is the only
precondition: when it is present, every one of its paths must exist before anything is
removed. When it is absent — which is what real filter text produces, since
`json-prune, a b c` has exactly one comma and the parser splits on commas — there is no
precondition at all and the paths are pruned from whatever carries them.

An earlier revision of this file claimed the opposite: that with no needle argument the paths
should gate themselves, and that a response carrying only `adSlots` had to be left alone. That
was wrong, and it was a regression that shipped. It also broke the rule below. Reverted.

The guard is still real when a second argument is present. uBlock's own `json-prune`
documentation is the source: the second parameter is the "list of space-separated properties
which must be all present for the pruning to occur".

### In-video ads were not going through any of that

Feed ads get hidden by the CSS rules, so the page looked blocked while pre-rolls kept
playing. Two separate causes, both found by reading an actual watch page rather than guessing.

The ad schedule never touches `JSON.parse` or `Response.json`. YouTube ships it as an inline
object literal:

```html
<script nonce="…">var ytInitialPlayerResponse = { … "adPlacements":[{"adPlacementRenderer":
{"config":{"adPlacementConfig":{"kind":"AD_PLACEMENT_KIND_START",
"adTimeOffset":{"offsetStartMilliseconds":"0"}}}}] … };</script>
```

…and hands that object straight to the player as `raw_player_response`. It is a global
variable assignment, so neither hook could ever see it. `json-prune` now installs an accessor
on `window.ytInitialPlayerResponse`. That works because a global `var` declaration does not
redefine a property the global object already has: it routes the initializer through the
existing setter. The hook only has to be in place before the page's script runs, which is what
document-start injection already guaranteed.

Worth knowing: the runtime `POST /youtubei/v1/player` response is *not* where this lives. On a
real page it carries `adBreakHeartbeatParams` and no `adPlacements` at all. The inline
bootstrap is the carrier.

### Listing both spellings is correct, not self-defeating

The filter being used was:

```
youtube.com##+js(json-prune, playerResponse.adPlacements playerResponse.playerAds
  playerResponse.adSlots adPlacements playerAds adSlots)
```

This entry previously claimed the rule could never fire, because both the wrapped and the bare
spelling are listed and no payload carries both. That reasoning was backwards. There is no
needle argument here, so there is no precondition to fail: the rule simply deletes every listed
path from every payload that has one. Listing both spellings is how a single rule covers a
player response nested under `playerResponse` *and* one at the top level, which is exactly what
uBlock's own YouTube rule does. An earlier revision also told users to drop the
`playerResponse.*` half, which would have silently broken feed responses that genuinely nest it.

### The real reason nothing worked: CSP blocked the scriptlet outright

Everything above was necessary and none of it was sufficient. Loading a watch page through the
proxy in a real browser and reading the console:

```
[ERROR] Executing inline script violates the following Content Security Policy directive
'script-src 'report-sample' 'nonce-gmtL5wrq9y9E5TLmgdIVzA' 'unsafe-inline' 'strict-dynamic' …'.
Note that 'unsafe-inline' is ignored if either a hash or nonce value is present in the source
list. The action has been blocked.
```

YouTube publishes a CSP nonce. That makes `'unsafe-inline'` inert, and the injected
`<script>` carried no nonce, so the browser refused to execute it. Every `##+js()` rule on
every CSP-hardened site was a silent no-op — the tag sat in the DOM, the hook was absent at
runtime, and nothing errored. This is why the `json-prune` reasoning above could look
convincing and still be untested: the scriptlet never ran at all.

Confirmation from the same page, before the fix: the script tag was present at document start,
`JSON.parse` was unpatched, and `window.ytInitialPlayerResponse` was a plain non-configurable
data property — the signature of the page's `var` creating a fresh global binding, which only
happens when the property did not already exist.

The fix reuses the nonce the page already publishes, because we are rewriting that same
response, so the value is already valid for it. `cspNonce` finds the first `nonce="…"` in the
document and `withCSPNonce` puts it on the generated tag. Pages with no nonce get a plain tag,
as before.

After the fix, in the same browser, on a real watch page:

- `JSON.parse` prunes, and `Response.prototype.json` prunes a real `AD_PLACEMENT_KIND_START`
  payload while leaving `videoDetails` and `streamingData` intact
- `ytInitialPlayerResponse`, `ytplayer.bootstrapPlayerResponse` and
  `ytplayer.config.args.raw_player_response` all report `adPlacements: false`
- no CSP violation in the console
- the video still plays: 854x480, 213.1s, `readyState 4`, no ad slot in the DOM and no ad class
  on `#movie_player`

### What was not needed

uBlock's YouTube filters also carry raw-body `$replace` rules for `/youtubei/v1/player` and
`/youtubei/v1/get_watch`, plus `trusted-replace-xhr-response` scriptlets and a rule blocking
googlevideo `initplayback`. None of that was implemented. The `Response.prototype.json` and
inline hooks already cover both carriers, so the response rewriter is skipped unless a real
leak shows up in testing.

### Server-side selector pre-filter was eating YouTube's rules

`filterSelectors` in `css_filter.go` dropped any selector whose class or id wasn't present
in the server's HTML. That is a good trade for the ~64K generic EasyList selectors and a bad
one for domain-scoped rules: YouTube is a Polymer app, so its ad containers are built by
JavaScript long after the HTML was served. Those selectors were being thrown away, and the
ad was never hidden.

Generic selectors still go through the pre-filter. Domain-scoped ones are now always
injected and left for the browser to match against the live DOM, which is what uBlock does.

### Everything was injected after the page's own inline scripts

Both the `<style>` tag and the scriptlets went in right before `</head>`. By then every
inline script in the head had already run, which is where YouTube sets `ytcfg` and where
the anti-adblock checks live. Any `set-constant` or `abort-on-property-*` rule was landing
too late to matter.

Injection now happens as the first thing inside `<head>`, so scriptlets win the race against
page scripts the same way they do in the extension.

### rc / remove-class resolved to nothing

`scriptletAliases` mapped `rc` to `remove-class`, but there was no `remove-class` in
`scriptletLibrary`, so both names produced an empty string and no error. Every filter using
them was silently dead.

### Scriptlet lookup rescanned the whole ruleset per page

`ElementHidingForDomain` caches per domain. `ScriptletsForDomain` did not, and it walks
every scriptlet rule in the list. uBlock Filters ships a couple thousand of them, so that
was a linear scan on every HTML response. Now cached alongside the element hiding.

### Rules were accepted and then ignored

`POST /api/rules` took any string. `#?#` lines were dropped with no warning, and an
unrecognised scriptlet name produced an empty string with no warning. Pasting a uBlock rule
and watching nothing happen had no way to tell you why.

Rules are now validated on the way in and rejected with the reason, and unsupported
constructs show up in the parse warnings instead of vanishing.

### Procedural cosmetic filters run against a real DOM

`#?#` filters were skipped outright. They are now evaluated on a parsed document instead of
thrown away. `:upward()`, `:has-text()`, `:min-text-length()`, `:matches-attr()`,
`:matches-path()`, `:others()` and `:not()` all work, as do the `:remove()`,
`:remove-attr()`, `:remove-class()` and `:style()` actions and `##^` HTML filters.

`:watch-attr()` and `:matches-css-before()` still don't. Both need a live document or the
page's resolved stylesheets, and the proxy only ever has one snapshot of the bytes YouTube
sent. They stay unsupported on purpose rather than half-working.

The selector matching is hand-rolled rather than pulled in as a dependency. The subset
uBlock filters actually use is small, and the procedural operators have to walk the tree
anyway, so a second engine would have been paying twice for the same traversal.

### The DOM pass could have cost a re-render on every page

Parsing and re-rendering is not free, and it is not free in correctness terms either. An HTML
parse normalizes the markup on the way out: void elements gain a slash, unquoted attributes
get quoted, attribute order follows the parser's. All of that is legal and browsers don't
care, but doing it to every page of every site just because someone once wrote a `#?#` rule
is a bad trade.

So the round trip happens only when it buys something. Two gates: a rule has to apply to the
host, and it has to match something. Miss either and the original bytes go to the client
untouched. `TestProceduralNoMatchLeavesBytesAlone` pins that down, because it is exactly the
kind of guarantee that erodes once someone adds an unconditional re-render later.

Script bodies, the doctype and entity references all survive the round trip, which is the
part that actually matters — YouTube's hydration breaks if any of those come back different.
`TestProceduralRoundTripPreservesScripts` checks them.

### Rules that select without acting still hide

`#?#.ad` with no trailing action operator is the common form, and it cannot be a node
removal: the page's own scripts hydrate against a specific tree shape, and yanking nodes out
of it breaks the app. A selector-only rule gets an `ublp-phid` class on each match plus one
`display: none` rule, which hides the same nodes CSS would have hidden in the extension
while leaving the tree intact.

## Known limits, still true

- The DOM pass sees the server-rendered document. Content that only exists after JavaScript
  runs is only reachable through the injected CSS, not through procedural filters.
- A cosmetic rule scoped to `www.youtube.com` does not match the apex `youtube.com` or
  `m.youtube.com`. `domainMatchesOrIsSubdomain` only walks downwards, so a `www.`-scoped
  filter needs its own entry if you care about those. YouTube redirects to `www`, so desktop
  is fine in practice; mobile is not.
- `#?#` rules are evaluated once per response. No live observation, so anything that changes
  the DOM later is out of reach.
- No re-compression. HTML is served uncompressed after injection.
