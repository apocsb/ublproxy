# Changelog

Running log of what changed and why. Newest at the bottom.

## Network-wide uBlock parity

Goal: make ublproxy block what uBlock Origin blocks, on YouTube especially, without a
browser extension. Started from three rules pasted into the portal:

```
youtube.com##ytd-ad-slot-renderer
youtube.com##ytd-rich-item-renderer:has(> ytd-ad-slot-renderer)
www.youtube.com##+js(json-prune, playerResponse.adPlacements playerResponse.playerAds playerResponse.adSlots adPlacements playerAds adSlots)
```

The first two already worked. The third did nothing. Chased that down and it turned into
the list below.

### json-prune only hooked JSON.parse

`internal/blocklist/scriptlets.go` patched `JSON.parse` and nothing else. YouTube pulls its
player and feed data from the Innertube API over `fetch`, and reads it with
`Response.prototype.json()`. Nothing ever called the patched `JSON.parse`, so the scriptlet
was dead code on the exact site it was written for.

Added a `Response.prototype.json` hook and brought the path syntax up to what uBlock
actually accepts: needle paths as a precondition, and the `[]`, `*`, `[-]`, `{-}` tokens for
arrays and for objects whose keys you can't predict.

### Server-side selector pre-filter was eating YouTube's rules

`filterSelectors` in `css_filter.go` dropped any selector whose class or id wasn't present
in the server's HTML. That is a good trade for the ~64K generic EasyList selectors and a bad
one for domain-scoped rules: YouTube is a Polymer app, so its ad containers are built by
JavaScript long after the HTML was served. Those selectors were being thrown away, and the
ad was never hidden.

Generic selectors still go through the pre-filter. Domain-scoped ones are now always
injected and left for the browser to match against the live DOM, which is what uBlock does.

### Everything was injected after the page's own inline scripts

Both the `<style>` tag and the scriptlets went in right before `</head>`. By then every
inline script in the head had already run, which is where YouTube sets `ytcfg` and where
the anti-adblock checks live. Any `set-constant` or `abort-on-property-*` rule was landing
too late to matter.

Injection now happens as the first thing inside `<head>`, so scriptlets win the race against
page scripts the same way they do in the extension.

### rc / remove-class resolved to nothing

`scriptletAliases` mapped `rc` to `remove-class`, but there was no `remove-class` in
`scriptletLibrary`, so both names produced an empty string and no error. Every filter using
them was silently dead.

### Scriptlet lookup rescanned the whole ruleset per page

`ElementHidingForDomain` caches per domain. `ScriptletsForDomain` did not, and it walks
every scriptlet rule in the list. uBlock Filters ships a couple thousand of them, so that
was a linear scan on every HTML response. Now cached alongside the element hiding.

### Rules were accepted and then ignored

`POST /api/rules` took any string. `#?#` lines were dropped with no warning, and an
unrecognised scriptlet name produced an empty string with no warning. Pasting a uBlock rule
and watching nothing happen had no way to tell you why.

Rules are now validated on the way in and rejected with the reason, and unsupported
constructs show up in the parse warnings instead of vanishing.

### Procedural cosmetic filters run against a real DOM

`#?#` filters were skipped outright. They are now evaluated on a parsed document instead of
thrown away. `:upward()`, `:has-text()`, `:min-text-length()`, `:matches-attr()`,
`:matches-path()`, `:others()` and `:not()` all work, as do the `:remove()`,
`:remove-attr()`, `:remove-class()` and `:style()` actions and `##^` HTML filters.

`:watch-attr()` and `:matches-css-before()` still don't. Both need a live document or the
page's resolved stylesheets, and the proxy only ever has one snapshot of the bytes YouTube
sent. They stay unsupported on purpose rather than half-working.

The selector matching is hand-rolled rather than pulled in as a dependency. The subset
uBlock filters actually use is small, and the procedural operators have to walk the tree
anyway, so a second engine would have been paying twice for the same traversal.

### The DOM pass could have cost a re-render on every page

Parsing and re-rendering is not free, and it is not free in correctness terms either. An HTML
parse normalizes the markup on the way out: void elements gain a slash, unquoted attributes
get quoted, attribute order follows the parser's. All of that is legal and browsers don't
care, but doing it to every page of every site just because someone once wrote a `#?#` rule
is a bad trade.

So the round trip happens only when it buys something. Two gates: a rule has to apply to the
host, and it has to match something. Miss either and the original bytes go to the client
untouched. `TestProceduralNoMatchLeavesBytesAlone` pins that down, because it is exactly the
kind of guarantee that erodes once someone adds an unconditional re-render later.

Script bodies, the doctype and entity references all survive the round trip, which is the
part that actually matters — YouTube's hydration breaks if any of those come back different.
`TestProceduralRoundTripPreservesScripts` checks them.

### Rules that select without acting still hide

`#?#.ad` with no trailing action operator is the common form, and it cannot be a node
removal: the page's own scripts hydrate against a specific tree shape, and yanking nodes out
of it breaks the app. A selector-only rule gets an `ublp-phid` class on each match plus one
`display: none` rule, which hides the same nodes CSS would have hidden in the extension
while leaving the tree intact.

## Known limits, still true

- The DOM pass sees the server-rendered document. Content that only exists after JavaScript
  runs is only reachable through the injected CSS, not through procedural filters.
- `#?#` rules are evaluated once per response. No live observation, so anything that changes
  the DOM later is out of reach.
- No re-compression. HTML is served uncompressed after injection.
